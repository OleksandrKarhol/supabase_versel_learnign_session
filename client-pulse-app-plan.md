# Client Pulse — App Plan

*Goal: not just a reporting tool — a small platform that exercises the breadth of Supabase + Vercel capabilities, using the Client Pulse reporting concept as the domain that makes each feature make sense.*

Every feature below exists for two reasons: it's something the domain plausibly needs, **and** it demonstrates a specific Supabase/Vercel primitive. That mapping is called out explicitly so this stays a learning vehicle, not just an app.

---

## 1. Feature list

| Feature | What it is in-domain | What it demonstrates |
|---|---|---|
| **Auth** | Rep/manager/admin sign in | Supabase Auth (email+password or magic link) |
| **Profile settings** | Name, avatar, notification prefs | `profiles` table + Storage (avatar upload) |
| **Role management** | Admin assigns Admin / Manager / Rep | Postgres enum + RLS keyed off role |
| **Access management** | Who can see which clients' reports | RLS policies, not app-layer checks |
| **User invites** | Admin invites a teammate by email | Edge Function (send email) + invite token flow |
| **Mock cron jobs** | Daily ticket/call sync, scheduled report generation | `pg_cron` **and** Vercel Cron, side by side, plus a manual "run now" for on-demand visibility |
| **Storage** | Generated HTML reports, avatars, raw transcript files | Supabase Storage + bucket-level RLS |
| **Tables with raw data** | Browsable calls/tickets/NPS per client | Straight Postgres tables, a "raw data" tab |
| **Reporting tab** | The actual Client Pulse report (styled per `demo.html`) | Everything above, composed into one view |
| **Chatting experience** | "Ask this client's data a question" | Simulated — templated/rule-based answers pulled from the mock tables, streamed with a typing effect. No real LLM call, no API key required |

This list is intentionally broader than "just render a report" — it's the checklist for the learning session's hands-on follow-up.

---

## 2. Roles & permission model

Three roles, stored on a `profiles` row linked to `auth.users`:

- **Admin** — manages users, roles, and invites; sees all clients and reports; can view/trigger the mock cron jobs.
- **Manager** — sees all reps' tracked clients and reports (rollup view); can reassign a tracked client between reps.
- **Rep** — can track up to N clients per quarter; sees only their own tracked clients, reports, and chat history.

Every access rule above is enforced as a Postgres **RLS policy**, not an `if` statement in the frontend — this is the direct callback to the learning session's RLS slide.

---

## 3. Data model (draft)

Not final — a starting point to refine once we scaffold.

- **`profiles`** — id (→ `auth.users`), full_name, avatar_url, role (`admin` / `manager` / `rep`), created_at
- **`invites`** — id, email, role, invited_by, status (`pending`/`accepted`/`expired`), token, expires_at
- **`clients`** — id, name, industry, plan, customer_since, arr, active_rooms, total_rooms, total_users, data_volume_gb
- **`tracked_clients`** — rep_id, client_id, quarter, requested_at *(enforces the "10 clients per quarter" quota)*
- **`calls`** — id, client_id, type (`sales`/`cs`), occurred_at, summary, themes (jsonb), transcript_storage_path
- **`tickets`** — id, client_id, subject, theme, sentiment, created_at, resolved_at
- **`nps_scores`** — id, client_id, score, csat, recorded_at
- **`reports`** — id, client_id, period_start, period_end, metrics (jsonb), synthesis_text, expansion_score, expansion_reasons (jsonb), html_storage_path, generated_at, status
- **`cron_runs`** — id, job_name, started_at, finished_at, status, detail *(so the mock cron jobs are visibly observable in the UI, not just invisible background magic)*
- **`chat_threads`** / **`chat_messages`** — scoped to a rep + a client, for the simulated chat experience (message content is generated by simple rules/templates over the tables above, not an LLM call)

## 4. Supabase feature map

| Supabase primitive | Used for |
|---|---|
| Auth | Login, invite-based signup |
| Postgres + RLS | Every access rule in the app |
| Storage | Generated report HTML, avatars, raw mock transcripts |
| Edge Functions | Generating the invite link/token, possibly report generation |
| pg_cron | One of the two scheduled-job demos (daily mock data sync), plus manual trigger |
| Realtime | Live status updates on `cron_runs` / `reports` while a job runs |

## 5. Vercel feature map

| Vercel primitive | Used for |
|---|---|
| Next.js on Vercel | The whole frontend + API routes |
| Preview deployments | Every branch, automatically |
| Env vars per environment | Supabase keys only for now — no LLM key needed since chat is simulated |
| Vercel Cron | The second scheduled-job demo (e.g. triggers scheduled report generation), deliberately alongside pg_cron so both approaches are visible |

## 6. App map (pages)

- `/login` — Supabase Auth
- `/accept-invite` — accept an invite token, set password
- `/dashboard` — a rep's tracked clients + at-a-glance KPIs
- `/clients/[id]` — **Reporting tab**: the Client Pulse report itself, styled per `demo.html`
- `/clients/[id]/data` — raw data tab: calls, tickets, NPS, browsable/filterable tables
- `/clients/[id]/chat` — chat experience scoped to that client's data
- `/admin/users` — role management + invites (Admin only)
- `/admin/jobs` — mock cron job monitor: history + a manual "run now" trigger (Admin only)
- `/settings/profile` — profile settings, avatar upload

## 7. Suggested build phases

Same "smallest slice first" philosophy as the learning session's hands-on section — each phase is runnable end to end before the next starts:

1. **Auth + roles + one client, read-only** — login, `profiles`, `clients` table, RLS by role, no reports yet.
2. **Raw data + reporting tab** — `calls`/`tickets`/`nps_scores`, one manually-triggered report, Storage for the rendered HTML, report view styled per `demo.html`.
3. **Invites + role/access management UI** — Admin screens, invite flow via Edge Function.
4. **Mock cron jobs + job monitor** — `pg_cron` job, a matching Vercel Cron job, `cron_runs` table, Realtime status in `/admin/jobs`.
5. **Chat experience** — simulated chat scoped to a client, templated responses pulled from `calls`/`tickets`/`nps_scores`, streamed with a typing effect for the UX.

---

## 8. Decisions locked in

- **Cron cadence**: daily, matching a realistic schedule — plus a manual "run now" button in `/admin/jobs` so a run can be triggered on demand during the session.
- **Chat scope**: simulated only, no real LLM call and no AI provider API key required. Per-client scope is enough — this can be revisited later if we decide to wire in real AI.
- **Invites**: mocked — generate a link/token shown in the UI to copy, no email provider needed.
- **Transcript storage**: raw mock transcripts stored as files in Supabase Storage, so Storage has real work to do beyond avatars/reports.

Net effect: the only external account we need for now is Supabase + Vercel — no email provider, no LLM API key.
